# Tool security review

Galaxy reviews the command and configfile templates of tools for places where a value a user controls can
leave the quotes or the argument it is written into: a text parameter, a collection element identifier, a
dataset name or metadata element, a group tag, a dataset's content, a user preference. Nothing from the tool is
run: the templates are compiled with Cheetah's compiler and the resulting syntax tree is analysed. A process
that prepares jobs reviews a tool when it prepares the tool's first job, and keeps the review as long as it
keeps the tool.

Before a job's command line is built, the values of the job are compared with the tool's findings. Two
options in `galaxy.yml` control what happens then:

- `tool_security_review` sets what a value may not do. Each level fails the jobs the one before it fails, and
  more:
  - `enforce_code` (the default): a value may not become code, such as starting a shell command, changing the
    program of another interpreter or the code of a configfile, or choosing the program that is run.
  - `enforce_data`: a value also stays the data it is meant to be. It may not name a path outside the job's
    directory, be read as an option, split into words that are options or paths, or change the structure of a
    data configfile. Element identifiers and dataset names that a template writes may not contain `/` or start
    with `-` or `~`.
  - `enforce_all`: a value also may not split into extra plain words or close its quotes.

  `log` only logs a warning for what `enforce_all` would fail, and `off` turns the review and the checks off.

- `tool_security_review_when_unsure`: for jobs the review cannot check, `strict` (the default) requires every
  value the job carries to be plain, and refuses every job of a tool none of whose values can be checked.
  `refuse` fails every such job, and `log` runs it and logs what `strict` would fail.

A plain value has no quotes, no `$ ; & | < > \ ( ) { } [ ] % # *`, no newline or tab, no word that starts with
`-`, and none of Galaxy's sanitizer tokens such as `__gt__`.

To see what the review finds in a tool, run

```console
$ python -m galaxy.tool_util.security path/to/tool.xml
```

## Refusal codes

Every refused job carries one or more codes: the message of the failed job starts with them
(`[shell-injection] This job was not run: ...`), and so does the warning Galaxy logs
(`Tool security review (shell-injection): job ...`).

The examples below are the cases of the review's declarative spec,
`lib/galaxy/tool_util/security/spec/`, which ships in `galaxy-tool-util`. Each case is a real tool XML file
and the jobs it refuses and runs. A job lists everything a template can read: parameter values (`inputs`),
datasets (`name`, `content`, `metadata`, `tags`), collections (element identifiers), the user's preferences,
and the review's settings (`config`). Galaxy's unit tests run every job through the evaluator that prepares
real jobs, in the mode of the job's `config` and in `log` mode. For the refused jobs that show `harm-marker`, they also build the
command with the review off and run it, to show that the value does harm without the review. They also
sweep every job: with the default settings, each value a job sets, each of a few preferences, and the user's
email and name in turn hold a value that starts a command, and the job must be refused or run without harm.

### `shell-injection`

A value can close the quotes around it, or is written unquoted, and start another shell command.

#### raw_text_shell_injection

A text value written past its sanitizer can close its single quotes and start a command.

Tool `raw_text_single_quoted.xml`:

```
echo '${word.value}' > '$out'
```

Refused

```
inputs:
  word: a';touch harm-marker;'
```

Runs: Command characters stay inside the quotes when no quote closes them.

```
inputs:
  word: a;b|c && d
```

#### ftpfile_param_shell_injection

An ftpfile param is written as the user's file names, with no sanitizer, and can close its single quotes.

Tool `ftpfile_param_single_quoted.xml`:

```
cat '$f' > '$out'
```

Refused

```
inputs:
  f: a';touch harm-marker;'
```

Runs

```
inputs:
  f: /dev/null
```

## Access patterns

The review also reports reads it cannot follow to a value of the job. A read by name (reflection) can
write any value without a finding about it, so it refuses every job of the tool. For the others, a job
is refused only when the review also sees the value written where it can do harm.
A case marked as a known bypass is a tool whose jobs run whatever their values.

### Reads the job check cannot see

#### `reflection`

Reaches objects by name (`getattr`, `__getattribute__`, `getVar` with a computed name, Python or Cheetah internals). The review loses track of what is read, `.unsanitized` values included.

Refused cases with it: `reflection_bypass`, `getvar_user_name`.

##### output_filter_vars

`vars()` in an output filter reaches Python objects, but Galaxy evaluates filters when it creates the outputs: nothing it reads is written into the command, which is checked as usual.

Tool `output_filter_vars.xml`:

```
echo '$label' > '$out'
```

Runs

```
inputs:
  label: a;b|c
```

#### `model-access`

Reads Galaxy's database objects (`.unsanitized`, `.dataset`, `.creating_job`, ...): names, metadata and parameters as users set them, without the sanitizer.

Refused cases with it: `raw_dataset_model`, `raw_dataset_history`.

#### `app-access`

Reads Galaxy's application object beyond its configuration (`$__app__.model`, ...), which reaches any data of the server.

##### app_model_read

The application object reaches any data of the server. The review flags the read but follows no value of it; this job runs because it writes a count.

Tool `app_model.xml`:

```
#set $users = $__app__.model.context.query($__app__.model.User).count()
echo '${users}' > '$out'
```

Runs

```
{}
```

##### output_size_limit_subscript

The allowance is of the attribute read alone: a subscript of the application object, here on the way to the same number, is flagged as a read of the application object. Galaxy's wrapper of the application object takes no subscript, so the tool goes that way only for a negative limit.

Tool `output_size_limit_subscript.xml`:

```
#if $__app__.config.output_size_limit < 0
python '$__tool_directory__/data_source.py' '$out' ${__app__['config'].output_size_limit}
#else
python '$__tool_directory__/data_source.py' '$out' 0
#end if
```

Runs

```
{}
```

#### `user-object`

Reads the user object with the sanitizer off. A preference read by its name is checked; anything else read from the user object is not.

Refused cases with it: `user_preference_shell_injection`, `user_object_unsanitized`.

#### `file-access`

Reads or inspects files on the server (`open()`, `os.path`, ...). The review traces `open()` of an input dataset as its content; any other file is not a value of the job.

Refused cases with it: `dataset_content_shell_injection`.

#### `template-code`

Runs Python the review cannot follow (`exec`, `compile`, imports of modules that start processes or open connections, `#include` of anything but a template macro, a lambda that reads more than its arguments or changes a value).

Refused cases with it: `include_dataset`, `template_macro_rebound`, `rewrites_and_template_code`, `lambda_late_binding`, `lambda_changes_a_list`, `template_code`.
